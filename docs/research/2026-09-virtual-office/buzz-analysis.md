## 에이전트 대화 모델 — 질문의 핵심

#### Buzz가 실제로 해결한 것

기존 방식에서 에이전트는 **봇 토큰**이다. 토큰은 앱에, 앱은 워크스페이스에, 워크스페이스는 벤더에 귀속되며, 어느 인스턴스가 실제로 행위했든 전부 "YourBot"으로 귀속된다. Buzz는 각 에이전트에게 **자체 Nostr 키페어·계정·권한**을 부여해 이 모델을 폐기한다. 사람과 에이전트가 동일한 이벤트 형식·동일한 신원 모델·동일한 감사 추적을 공유한다.

### 동작 패턴 (공식 데모 기준)

    사람이 @멘션으로 에이전트에 과제 지시
      → 에이전트가 스레드 안에서 계획 수립
      → 다른 에이전트에게 멘션으로 하위 과제 인계
      → 패치 생성(Buzz git 또는 GitHub PR)
      → 최종 리뷰를 사람에게 핑

- 에이전트가 채널 멤버십을 직접 보유하므로, 한 스레드에서 **복수 에이전트를 동시 태그**해 병렬 작업을 지시할 수 있다.
- Block은 하나의 프론티어 에이전트가 더 저렴·빠른 에이전트 무리를 지휘해 조사·구축·테스트·리뷰를 병렬 수행하는 운용을 소개한다. 조율 수단은 **평범한 채널 멘션**이다.
- 가장 주목되는 활용은 **에이전트 간 상호 비평**이다. 한 에이전트가 초안을 내면 다른 에이전트가 검토·지적·수정 제안을 같은 스레드에서 수행한다. 사람이 두 도구 사이를 복사해 나르지 않는다.
- 기능 브랜치 = 채널. 대화·패치·CI 결과·리뷰 결정이 한 스레드에 모여 **"다른 시스템에 가서 맥락 확인"이 사라진다**.

#### 우리 설계와의 접점

현 v2 계약에는 `vote_call`/`vote_cast`/`vote_result`가 있으나, **peer들이 실제로 논의하는 매체가 없다**. 투표는 있는데 회의가 없는 구조다. Buzz가 정확히 그 빈칸을 채운다.

## Hermes 공식 통합 — 결정적 변수

Nous Research가 **Hermes Agent ↔ Buzz 공식 통합 문서를 이미 게시**했다. 우리는 T3610·Raspi5P 양쪽에 Hermes를 설치해 두었으므로, 어댑터 자체 개발 부담이 사실상 소멸한다.

|                 | ① 데스크톱 런타임                          | ② 릴레이 브리지(ACP)                              | ③ 네이티브 게이트웨이                                  |
|-----------------|--------------------------------------------|---------------------------------------------------|--------------------------------------------------------|
| **구조**        | Buzz Desktop이 Hermes를 로컬 하네스로 스폰 | `buzz-acp`가 채널을 `hermes acp`에 stdio로 브리지 | Hermes 게이트웨이가 Buzz를 정식 메시징 플랫폼으로 편입 |
| **Hermes 위치** | 데스크톱, Buzz가 실행                      | 서버, `buzz-acp`가 실행                           | 자체 게이트웨이(Telegram 등과 동렬)                    |
| **적합 용도**   | 무설정 체험                                | Buzz가 전송을 소유하는 호스팅 에이전트 신원       | **메모리·스킬·승인·크론·세션 전부 보존**               |
| **인바운드**    | ACP stdio                                  | ACP stdio(릴레이 WS 경유)                         | NIP-42 인증 Nostr WebSocket(폴링 폴백)                 |
| **판정**        | `제외`         | `보조`                | `채택 후보`                 |

③은 채널·DM·멘션 게이팅·스레드 응답·리액션·이미지·크론 전달(`deliver=buzz`)을 지원하면서 **Hermes 자체의 승인·메모리·세션 관리를 그대로 유지**한다. 우리 설계에서 Honcho 학습 누적(원칙 1의 세로획)이 핵심이므로, 메모리를 보존하는 ③ 외에는 선택지가 없다.

공식 문서 주의사항: ①/②와 ③은 신원·전송이 다르므로 ③은 **전용 Nostr 키페어**로 운용해야 한다. 어댑터가 relay+pubkey 쌍에 스코프 락을 걸어 두 Hermes 프로파일이 하나의 Buzz 신원을 동시에 구동하는 사고를 막는다.

#### 리스크 1의 의미 — 원칙 4 직접 충돌

도구 권한 자동 승인은 우리의 "사람 = 최종 결정자" 원칙과 정면 충돌한다. 완화 수단은 존재한다: `buzz-acp`는 기본 모드가 **owner-only**이며, 소유자 공개키가 확인되지 않은 에이전트는 어떤 이벤트에도 응답하지 않는다. `--respond-to`로 `owner`(기본) / `allowlist` / `anyone` / `nobody`를 선택하고, 소유자는 `!cancel`·`!rotate` 등 제어 명령을 게이트보다 먼저 처리시킬 수 있다. **도입 시 owner-only 고정은 협상 대상이 아니다.**

## 핵심 판단

**Buzz는 대체재가 아니라 부품이다.**

Buzz를 **뼈대 내부의 에이전트 간 대화 기질(substrate)**로만 도입하고, 살·Gitea·n8n·OpenProject·Honcho는 전부 유지한다. Buzz의 포지·워크플로 엔진·호스팅 릴레이는 **채택하지 않는다**.

### 판단 근거 4가지

- **공백이 실재한다.** v2 계약에 투표는 있으나 논의 매체가 없다. 자체 구현하면 채널·스레드·팬아웃·서명·감사체인을 전부 만들어야 하고, Buzz는 이를 Apache 2.0으로 이미 제공한다.
- **어댑터 비용이 소멸했다.** 6월 프레임워크 비교 당시 Hermes의 약점은 "어댑터 직접 개발 필요"였다. Nous의 공식 Buzz 통합(특히 ③ 네이티브 게이트웨이)이 이 약점을 제거했다. **6월 판단의 전제가 바뀌었다.**
- **전면 채택은 근거가 없다.** 운영 1개월, 세분 도구 인가 미성숙, 기본 개방 가입, 비암호화. Gitea는 백업 스크립트까지 검증된 정본이고 n8n은 정문의 단일 통과 지점이다. 검증된 것을 1개월짜리로 교체할 이유가 없다.
- **중복 채택은 감사 이중화를 낳는다.** Buzz 포지를 쓰면 Gitea와 Buzz 두 곳에 코드 이력이 갈라진다. 의료기기 조직에서 이력 분기는 그 자체가 결함이다.

### 이벤트 원천 결정 `제안`

가장 어려운 지점이다. Buzz 릴레이도 이벤트 로그이고 우리 계약 v2도 이벤트 로그다. 둘을 병렬 운용하면 감사 원천이 둘이 된다.

**결정: 계약 v2를 의미 계약(semantic contract)으로 유지하고, Buzz는 교체 가능한 전송·저장 후보로 취급한다.** 즉 kind 이름·필드 정의는 우리 것을 정본으로 두고, Buzz 채택 시 Buzz kind 번호에 **매핑**한다. 파일럿이 실패해도 계약은 살아남는다. 파일럿이 성공하면 NAS JSONL은 Buzz 릴레이의 **사영(projection)**으로 격하한다.

## 도입안 — 격리 파일럿

    [Buzz 릴레이]  T3610 · Docker · owner-only · 내부망 한정
          │  NIP-42 인증 WebSocket
          ├── Hermes peer #1 (ra_us)   ── 전용 Nostr 키페어
          ├── Hermes peer #2 (ra_eu)   ── 전용 Nostr 키페어
          └── 사람 계정 1              ── 소유자, 전 에이전트의 owner
          │
          │  읽기 전용 브리지 (제안: n8n 폴러 또는 buzz-cli)
          ▼
    [계약 v2 JSONL]  DS224+ NAS — 정본 의미 계약, 사영으로 유지
          ▼
    [살]  가상 오피스 — 변경 없음, 계속 JSONL만 읽음

- **살은 이번 파일럿에서 손대지 않는다.** 계약 v2 JSONL만 계속 읽으므로 관찰자 원칙(6)이 그대로 보존된다.
- Buzz→JSONL 브리지는 **단방향 읽기**. 살은 Buzz의 존재를 모른다.
- 파일럿 채널은 1개(`#matching-review`)로 한정. 실제 과제는 **사안 매칭에 대한 peer 간 상호 비평** — Buzz의 가장 검증된 활용 패턴이자 우리에게 가장 필요한 기능이다.
- Gitea·n8n·OpenProject·Honcho·살 — 전부 무변경.

## 권고

**조건부 도입 — 격리 파일럿 승인 권고**

Buzz는 우리 설계의 실제 공백(에이전트 간 논의 매체)을 정확히 채우고, Hermes 공식 통합이 6월 판단의 전제였던 "어댑터 개발 부담"을 제거했다. 동시에 운영 1개월·자동 도구 승인·비암호화라는 사실이 전면 채택을 배제한다. 따라서 **격리 파일럿**이 유일하게 근거 있는 선택이다.
