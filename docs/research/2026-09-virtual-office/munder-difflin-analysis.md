## Hive 프로토콜 해부

HIVE.md는 에이전트 협업 계층의 설계 정본이다. 우리에게 중요한 것은 앱이 아니라 이 프로토콜이다.

### 확정된 설계 결정 5가지

| \#  | 결정                                  | 근거                                                                                                                                                                                                                                  |
|-----|---------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1   | **git = 조율·감사 계층, 단일 커미터** | 다수 동시 에이전트에서 `.git/index.lock` 손상을 피하기 위해 **메인 프로세스만 커밋**. 에이전트는 git을 호출하지 않고 평문 파일만 쓴다                                                                                                 |
| 2   | **파일당 단일 기록자**                | 각 에이전트는 자기 `agents//` 안에만 쓴다. 교차 전달은 라우터가 발신자 `outbox/`에서 수신자 `inbox/`로 옮긴다. **두 프로세스가 한 파일을 쓰는 일이 없다**                                                                         |
| 3   | GOD 모드 자율성, 네이티브 HITL        | 특권 에이전트가 교차 트래픽을 조정. 일상 요청은 자체 해결, 파괴적 작업·지출·범위 변경·해소 불가 충돌만 사람에게 `원칙 3·4 충돌 — §7`                                                                      |
| 4   | **메모리는 마크다운 우선**            | 에이전트별 `memory.md` + 공유 블랙보드, 키워드 회수가 부족할 때 SQLite FTS 인덱스. 5–15 에이전트 규모에서 **중량 벡터 계층은 불필요하며 구조적으로 부적합**하다고 명시 — 그들은 에이전트 런타임을 소유하려 하지만 여기 런타임은 CLI다 |
| 5   | 자율 루프 = Stop 훅                   | 작업을 마친 에이전트가 Stop 훅으로 인박스를 비운다. 훅이 차단 결정을 반환해 계속 일하게 하되 무한루프 방지 플래그로 보호                                                                                                              |

### 온디스크 레이아웃

    hive/
      PROTOCOL.md        # 에이전트용 계약 — 기억법·메시지 규약
      registry.json      # 로스터: 에이전트·역할·역량·상태·좌석
      board.md           # 공유 블랙보드 / 공동 작성 계획
      tasks.json         # 과제 원장 (id·담당·명세·상태·결과 참조)
      log.jsonl          # append-only 이벤트 피드 → UI 활동 스트림 구동
      agents//
        identity.md      # 나는 누구·역할·역량   (시작 시 읽음)
        memory.md        # 장기 기억           (시작 시 읽고, 배우며 덧씀)
        inbox/           # 나에게 전달된 메시지 — -.json
        inbox/.done/     # 처리 완료분 — 삭제하지 않고 감사용 보존
        outbox/          # 내가 보낼 메시지 — 라우터가 비움
        cursor.json      # { lastProcessed } — 재처리 방지

- **메시지 1건 = JSON 파일 1개.** 임시파일 + 원자적 rename으로 기록. 공유 메일박스 파일을 공동 편집하지 않는다 — git에서 충돌하기 때문.
- `log.jsonl`은 append-only이며 소비자가 각자 커서를 관리한다.
- `board.md`만이 유일하게 공동 편집되는 파일이며, 충돌 회피를 위해 **단일 서기**를 거친다.

#### 우리 설계와의 관계

`log.jsonl` append-only + 소비자 커서 = 우리 계약 v2의 JSONL 구조와 **동일**. 좌석(seat)이 registry에 있는 것도 우리 §5 공간 문법과 같다. 즉 이 프로젝트는 우리가 설계한 것을 **이미 구현해 1,159 커밋 운영**한 사례다.

## 메시지 스키마와 루프 방어

FIPA-ACL/KQML에서 **화행(speech act)** 하나만 취하고 LISP 문법은 버린 7개 필드 설계.

    {
      "id":             "2026-05-30T14-03-11-123Z-a1b2",  // 시간순 정렬 가능
      "conversation":   "conv-7f3",                        // 스레드 묶음
      "in_reply_to":    " | null",
      "from":           "agent.researcher",
      "to":             "agent.coder | god | broadcast",
      "act":            "request | inform | propose | query | agree | refuse | done",
      "subject":        "짧은 사람용 요약",
      "body":           "자유 텍스트 / 마크다운 / 구조화 페이로드",
      "hops":           3,        // 답신마다 증가, 상한 초과 시 차단
      "requires_reply": true,     // request/query/propose만 답신 의무
      "needs_human":    false,    // 라우터·조정자가 에스컬레이션으로 전환 가능
      "created_at":     "ISO-8601"
    }

### 안티 라이브락 규칙 `가장 큰 수확`

| 규칙           | 내용                                                                               |
|----------------|------------------------------------------------------------------------------------|
| 답신 의무 제한 | `request`/`query`/`propose`만 답신을 의무화한다. 순수 `inform`/`done`은 **종결형** |
| 홉 카운터      | 모든 답신이 `hops`를 증가시킨다                                                    |
| 홉 상한        | 상한을 넘으면 두 에이전트가 영원히 순환하도록 두지 않고 조정자가 에스컬레이션      |
| 멱등성         | 이미 처리한 `id`를 다시 봐도 무동작 — 커서로 보장                                  |
| 재처리 방지    | 처리된 메시지는 `inbox/.done/`으로 이동, 삭제하지 않음                             |

#### 우리 설계의 공백

계약 v2에는 **루프 방어가 전혀 없다.** `corr` 체인만 있고 홉 카운터·답신 의무 구분·상한이 없다. Hermes peer 다섯이 서로 매칭을 비평하기 시작하면 `ra_us → ra_eu → ra_us` 핑퐁이 토큰 예산을 소진할 때까지 돌 수 있다. 이것은 이론적 위험이 아니라 **MD가 실제로 겪고 문서화한 위험**이다.

## 우리 설계의 결손 4건

MD와 대조해 드러난 우리 계약 v2의 실제 구멍이다. Buzz 분석에서는 보이지 않았던 항목들이다.

| \#  | 결손                      | 결과                                                                                                            | MD의 해법                                                                 |
|-----|---------------------------|-----------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------|
| D1  | **화행 계층 부재**        | 이벤트가 "무슨 일이 있었나"만 기록하고 "무엇을 요구하는가"를 표현하지 못함. 수신자가 응답 의무를 판정할 수 없음 | `act` 7종 + `requires_reply`                                              |
| D2  | **루프 방어 부재**        | peer 간 무한 핑퐁 시 예산 소진까지 정지 수단 없음                                                               | `hops` 상한 + 답신 의무 제한 + 커서 멱등성                                |
| D3  | **동시 쓰기 규율 부재**   | 다수 peer가 Gitea에 동시 커밋 시 `index.lock` 손상 가능                                                         | 단일 커미터 + 파일당 단일 기록자 + 임시파일·원자적 rename                 |
| D4  | **폭주 차단 사다리 부재** | 정책은 일시정지/재개 2단계뿐. 루프·에러 폭주·예산 초과의 점진 대응 없음                                         | 서킷 브레이커 — **조정(steer) → 제약(constrain) → 정지(stop)** 3단 사다리 |

D1~D4는 전부 **명세 수준의 결손**이며, 어떤 제품을 도입하든 우리가 채워야 한다. 그리고 MD가 그 명세를 MIT로 공개해 두었다.

#### 읽어야 할 것

Buzz와 MD는 **경쟁 제품이 아니라 서로 다른 계층**이다. Buzz는 전송·신원 계층(네트워크), MD는 프로토콜·규율 계층(의미)에서 강하다. 우리에게 지금 부족한 것은 **후자**다.

## 판단 수정

#### 직전 세션 권고의 수정

직전 보고에서 **Buzz 격리 파일럿을 우선** 권고했다. MD 분석 결과 **순서를 바꾼다.** 이유는 셋이다.

- **비용 비대칭.** agent↔agent 대화라는 동일 목적을 Buzz는 Postgres+Redis+S3+Rust 릴레이로, MD는 git 저장소 하나로 달성한다. T3610의 Honcho 자원 경합이 이미 기재된 상태에서 전자를 먼저 시도할 이유가 없다.
- **결손이 전송이 아니라 의미에 있었다.** 우리에게 없던 것은 WebSocket이 아니라 화행·홉 상한·단일 기록자 규율(D1–D4)이었다. Buzz를 도입해도 이 넷은 여전히 비어 있다.
- **프로토콜은 의존성이 아니다.** MD의 hive 설계는 MIT 명세다. 앱을 설치하지 않고 **규약만 이식**할 수 있으며, 이식 비용은 문서 작업이고 되돌릴 것이 없다.

**MD는 프로토콜을 주고, Buzz는 전송을 준다.**

프로토콜을 먼저 확정하고, 전송은 필요가 증명된 뒤에 고른다. Buzz 파일럿은 **취소가 아니라 후순위**다 — 다중 호스트·암호학적 신원이 실제로 필요해지는 시점의 후보로 유지한다.

## 충돌 — GOD 에이전트

MD의 조율 모델은 우리 불변 원칙 두 개와 정면 충돌한다. 이 절은 **채택하지 않는 이유**를 명확히 하기 위한 것이다.

| MD의 구조                                                                             | 우리 원칙                                  | 판정                               |
|---------------------------------------------------------------------------------------|--------------------------------------------|------------------------------------|
| 특권 GOD 에이전트가 로스터·라우팅·조정·블랙보드 서기·과제 원장을 모두 소유            | **원칙 3** 중앙 두뇌 없음 — 판단 분산      | `배제` |
| 일상 요청은 GOD이 자체 해결하고 시스템은 완전 자율 유지. 임계 항목만 사람에게         | **원칙 4** 사람 = 최종 결정자              | `배제` |
| 에스컬레이션 정책이 GOD의 시스템 프롬프트에 있음 — 코드가 아니라 프롬프트가 주 제어면 | **원칙 9**(config-as-code, 이력·리뷰·롤백) | `배제` |

#### 대체 설계 `제안`

GOD의 **기능**은 필요하지만 **인격**은 필요 없다. 우리 구조에서는 이미 담당자가 있다.

- 라우팅·전달·홉 집계 → **n8n** (기존 배관 주체, 판단 없는 기계)
- 과제 원장 → **OpenProject WP** (기존)
- 로스터 → **Gitea config** (원칙 9, PR·리뷰·롤백)
- 조정·에스컬레이션 → **사람** (원칙 4). 자동 해결 없음

즉 **GOD을 해체해 기존 4개 주체에 분배**한다. 어느 것도 새로 만들 필요가 없다.

## 도입안 — 프로토콜 이식

앱이 아니라 규약을 가져온다. 설치·의존성·컨테이너 추가가 **0**이다.

    [정문]  n8n webhook  ── 사람 명령 (기존)
       │
       ▼
    [hive]  Gitea 저장소 1개 — 단일 커미터(n8n), 파일당 단일 기록자
       ├─ registry/           로스터 = config-as-code (원칙 9)
       ├─ log.jsonl           append-only = 계약 v2 그대로
       └─ agents//
            inbox/  outbox/  cursor.json     ← MD 규율 이식
       │
       ├─ Hermes peer ra_us  ── outbox에 쓰기만, git 미호출
       ├─ Hermes peer ra_eu  ── 동일
       └─ 라우터 = n8n       ── outbox → inbox 이송, 홉 집계, 상한 시 사람 에스컬레이션
       │
       ▼ 단방향 읽기
    [살]  가상 오피스 — log.jsonl만 읽음. 무변경 (원칙 6 보존)

### 이식하는 규율 6가지

| \#  | 규율                  | 우리 적용                                                                        |
|-----|-----------------------|----------------------------------------------------------------------------------|
| P1  | 단일 커미터           | n8n만 Gitea에 커밋. Hermes peer는 평문 파일만 쓴다 — `index.lock` 손상 원천 차단 |
| P2  | 파일당 단일 기록자    | 각 peer는 `agents//` 내부만. 교차 전달은 라우터가 수행                    |
| P3  | 메시지 1건 = 파일 1개 | 임시파일 + 원자적 rename. 공유 메일박스 파일 금지                                |
| P4  | 커서 멱등성           | `cursor.json`으로 재처리 방지, 처리분은 `.done/`에 감사 보존                     |
| P5  | 화행 + 답신 의무      | 계약 v2에 `act`·`requires_reply` 추가 (§9)                                       |
| P6  | 홉 상한               | `hops` 추가. 상한 도달 시 **사람**에게 에스컬레이션 (GOD 아님)                   |

P1~P4는 **구현 규율**, P5~P6은 **계약 변경**이다. 후자만 계약 v2.1로 문서화하면 되고, 전자는 Phase 1 구현 시 지키면 된다.

## 계약 v2.1 초안 제안

additive-only 규칙 준수 — 기존 필드 삭제·의미 변경 없이 4개 필드만 추가한다.

    {
      "v": 2.1,
      "id": "evt_20260819_000132",
      "ts": "2026-08-19T09:12:33+09:00",
      "workspace": "work",
      "actor": "ra_us",
      "kind": "matching",
      "case": { "wp": 1042, "regime": "US" },
      "payload": { },
      "artifacts": [ ... ],
      "cost": { ... },
      "corr": "evt_20260819_000130",

      // ── v2.1 추가 ──────────────────────────────
      "to":             "ra_eu | broadcast | human",   // 수신자 (신규)
      "act":            "request | inform | propose | query
                         | agree | refuse | done",     // 화행 (신규)
      "requires_reply": true,                          // request/query/propose만 true
      "hops":           3                              // 답신마다 증가, 상한 시 사람 호출
    }

| 필드             | 규칙                                                                    |
|------------------|-------------------------------------------------------------------------|
| `to`             | 없으면 관찰 이벤트(기존 v2 동작). 있으면 대화 이벤트                    |
| `act`            | `inform`·`done`은 종결형 — 답신 금지                                    |
| `requires_reply` | `request`/`query`/`propose`에서만 true 허용                             |
| `hops`           | 상한값은 `운영 실측 후 설정`. 초기값 미확정 |

**기존 kind와의 관계:** `vote_call`은 `act:"query"`, `vote_cast`는 `act:"inform"`, `handoff`는 `act:"request"`로 자연 매핑된다. 즉 v2의 kind 설계는 그대로 살고, 화행이 **직교 축으로 추가**될 뿐이다.

## 권고

**프로토콜 이식 즉시 · Buzz 후순위**

MD의 hive 규약(화행 7종·홉 상한·단일 커미터·파일당 단일 기록자·커서 멱등성)을 계약 v2.1로 이식한다. 설치·의존성 추가가 없고, MIT 명세이며, 실패해도 되돌릴 것이 문서뿐이다. Buzz 파일럿은 취소하지 않되 Phase 4로 미룬다.

### 이 판단의 근거를 한 줄로

우리에게 없던 것은 **메시지를 나를 배관이 아니라, 대화가 끝나게 만드는 규칙**이었다. Buzz는 전자를 주고 MD는 후자를 준다. 배관은 이미 n8n과 Gitea로 있다.

### 불변 원칙 영향

| 원칙                 | 영향                                                                        |
|----------------------|-----------------------------------------------------------------------------|
| 3 중앙 두뇌 없음     | `강화` — GOD 배제, 라우터는 판단 없는 기계      |
| 4 사람 = 최종 결정자 | `강화` — 홉 상한 도달 시 GOD이 아니라 사람 호출 |
| 6 관찰자 구조        | `유지` — 살 무변경, 단방향 읽기                 |
| 8 목업 = 계약        | `강화` — additive-only로 4필드만 추가           |
| 9 명명 이원화        | `유지` — `to`/`from`에 actor ID만               |

9개 축 중 **충돌 0, 강화 4, 유지 5**. Buzz안(충돌 1·긴장 1)보다 정합성이 높다.
