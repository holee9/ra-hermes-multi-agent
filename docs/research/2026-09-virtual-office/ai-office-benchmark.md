## 0. 철학 리마인드 — 불변 축과 v2에서의 생존 방식

| # | 원칙 【불변】 | 확정 내용 | v2에서의 적용 |
|---|---|---|---|
| 1 | T자형 성장 | 가로획 = llm-wiki·ra-project·MD-process 단방향 참조 / 세로획 = Honcho 학습 누적 | 변경 없음. 살은 성장에 관여하지 않고 성장의 **결과를 표시**만 함 |
| 2 | 프랙탈 + 벌집 | workspace = 조직 단위, 같은 구조 자기복제. 분산·상호지탱 | **층 = workspace**로 시각 문법화(§5). 새 workspace = 증축 |
| 3 | 중앙 두뇌 없음 | 판단 분산, 집계 규칙, 배관은 n8n | 살은 두뇌가 아님을 유지. 명령도 살이 판단하지 않고 정문으로 배달만(§3) |
| 4 | 사람 = 최종 결정자 | 3점 사후 평가. 완료·재오픈 사람 전용(불변 고정 규칙) | 살의 모든 쓰기성 행위(재개 버튼, 채용 승인)는 **사람 명령의 배달**이지 살의 권한이 아님 |
| 5 | 부재 기반 성장 | 부재가 패턴으로 확정될 때만 충원. 같은 철학=스킬, 독립 직능=에이전트 | **빈 좌석 = 부재의 시각화** + absence 이벤트 카운터 → 증거 기반 채용(§8) |
| 6 | 관찰자 구조 | 살은 활동 기록 읽기만, 운영 불개입. 뼈대는 살의 존재를 모름 | **형식적으로 완전 보존**. 살→뼈대 직접 쓰기 경로 0개(§3) |
| 7 | 기록 재생 = 정직한 표현 | 실시간 아닌 기록 재생. 일 있을 때만 캐릭터가 움직임 | 원칙의 본질은 "연출 금지". 실제 이벤트의 실시간 tail은 정직함 — SSE tail + 리플레이 병행(§4) |
| 8 | 목업 = 계약 | 뼈대 출력 형태(conclusion·투표·매칭·3점평가) 고정, DATA_SOURCE만 교체 | 계약을 **이벤트 봉투 v2**로 확장(§4). 목업 선개발 → 소스 교체 구조 유지 |
| 9 | 명명 이원화 | 뼈대 = ra_us/ra_eu/ra_kr 등 기계 ID / 살 = Mike·Theo·Sam·Margot·Olly·Finn·Leo·Gus | 변경 없음. 이벤트는 actor ID만 실림, 이름 매핑은 살 내부(§4) |

**리마인드 결론:** 9개 축 중 폐기·완화되는 것은 없다. v2는 원칙의 **표현력을 키우는 확장**이며, 유일한 긴장(관찰자 vs 양방향)은 §3에서 구조적으로 해소한다.

## 3. 핵심 종합 — 정문과 창문

**충돌 지점.** AI Office는 UI가 곧 제어면이자 관찰면인 **단일 평면**이다. 우리의 불변 원칙 6은 살→뼈대 쓰기를 금지한다. 이 충돌을 다음과 같이 해소한다.

**해소 원리: 명령은 정문으로, 관찰은 창문으로.**

- 사람의 명령권은 살 이전부터 존재한다(메일 재전송, OpenProject 직접 조작). 원칙 6이 제한하는 것은 **살이라는 시스템**이지 사람이 아니다.
- 따라서 살에 컴포저를 두되, 발신은 뼈대의 **기존 정문**(n8n webhook)으로만 나간다. 살 프로세스는 뼈대 상태를 1비트도 직접 쓰지 않는다.
- 명령의 효과는 뼈대가 남긴 활동 이벤트로 되돌아와 창문(읽기 전용 스트림)에서 관찰된다. 살은 자신이 보낸 명령의 결과조차 **관찰로만** 안다.

```
[사람] ──명령──▶ 정문: n8n webhook ─┬─ Gmail(기존 mail-triage)
   │                                ├─ OpenProject 직접 조작
   │                                ├─ Telegram 봇 【제안】
   │                                └─ 오피스 컴포저 【제안】
   │                                        │
   │                     [뼈대] Hermes peers + Honcho + n8n + OpenProject
   │                                        │ append-only 활동 이벤트 (계약 v2)
   │                                        ▼
   │                     [창문] 읽기 전용 스트림 게이트웨이 (JSONL + SSE tail)
   │                                        ▼
   └──관찰──────────────── [살] 가상 오피스 (층=workspace, 재생+실시간, 스크러버)
```

**결과:** 뼈대는 여전히 살의 존재를 모른다(오피스 컴포저는 뼈대 입장에서 여러 정문 채널 중 하나일 뿐). 관찰자 구조는 형식적으로 완전 보존되며, 사람은 조작 콘솔을 얻는다. AI Office가 단일 평면이라 권한·장애가 UI에 집중되는 것과 달리, 우리는 명령 경로와 관찰 경로가 분리되어 **감사 가능하고 안전**하다.

## 4. 활동 이벤트 계약 v2

v1 계약(conclusion·투표·매칭·3점평가)을 포괄하는 봉투(envelope)로 확장한다. **additive-only** — 필드 추가만 허용, 삭제·의미 변경 금지(하위 호환 규칙).

### 4.1 봉투 스키마 【제안】

```json
{
  "v": 2,
  "id": "evt_20260819_000132",
  "ts": "2026-08-19T09:12:33+09:00",
  "workspace": "work",
  "actor": "ra_us",
  "kind": "matching",
  "case": { "wp": 1042, "regime": "US" },
  "payload": { },
  "artifacts": [
    { "type": "xlsx", "name": "검증표.xlsx", "ref": "gitea://ra-ops/artifacts/1042/검증표.xlsx" }
  ],
  "cost": { "model": "qwen3-gx10", "in_tokens": 1820, "out_tokens": 640 },
  "corr": "evt_20260819_000130"
}
```

- `actor`는 뼈대 ID만 싣는다(원칙 9). Mike 등 이름 매핑은 살 내부 테이블.
- `corr`는 원인 이벤트 참조 — 살에서 스레드/애니메이션 연결에 사용.
- `cost`는 §7 거버넌스의 데이터 원천.

### 4.2 kind 목록 【제안】

| kind | 의미 | payload 핵심 | v1 대응 |
|---|---|---|---|
| `case_open` | WP 생성 관찰(정문 유입 결과) | source(mail/office/telegram/op), title | — |
| `matching` | 사안-전문가 매칭 | decision, confidence, basis[] | 매칭 |
| `comment` | WP 코멘트 | text_ref | conclusion 일부 |
| `handoff` | 규제권 간 이관·참조 | to_actor, reason | — |
| `vote_call` / `vote_cast` / `vote_result` | 투표 소집/투표/집계 | question·options / choice / tally·decision | 투표 |
| `eval3` | 사람 3점 사후 평가 | score, target_evt | 3점평가 |
| `artifact` | 산출물 발생 | artifacts[] 채움 | — |
| `absence` | 매칭 실패·직능 공백 관찰 | gap_tag, case | — (§8 원천) |
| `infra` | 호스트 상태(Finn·Leo·Gus) | host, metric, level | — |
| `policy` | 예산·동시성 정책 발화 | action(pause/resume/throttle), reason | — (§7 원천) |
| `hire_proposal` | 부재 임계 도달 | gap_tag, count, window | — (§8 원천) |

- `vote_result` 집계 주체는 n8n — ConsensusEngine 미구현 사실(6월 확정) 반영. 【미결】집계 구현 위치(n8n vs Hermes 직접)는 6월 미결 항목을 계승.
- 완료·재오픈은 이벤트 kind가 **없다** — 사람 전용 행위는 OpenProject에서만 일어나고, 살은 WP 상태 변화를 `case_open`/`comment` 수준으로 관찰만 한다(원칙 4 보존).

### 4.3 전송·저장 【제안】

- append-only JSONL. **append 주체 = n8n**(모든 배관의 통과 지점), 저장 = DS224+ NAS, tail relay(SSE) = Raspi5P.
- 근거: 6월 체크리스트의 T3610 자원 경합(Honcho ↔ ra-med-bot) 항목 — T3610에 relay를 두지 않는다.
- 살은 이 스트림만 읽는다. 목업 모드 = 동일 스키마의 JSONL 파일 재생 → `DATA_SOURCE` 교체 구조(원칙 8) 그대로.

## 5. 공간 문법 — 맵을 조직 구조의 시각 언어로

AI Office의 맵은 테마 장식이다. 우리는 맵 자체가 설계 철학을 발화하게 한다. 【제안】

| 공간 요소 | 의미 | 원칙 대응 |
|---|---|---|
| **층 = workspace** | 1F 업무(Mike·Theo·Sam·Margot·Olly + 사람 아바타), 2F 인프라(Finn·Leo·Gus), 3F 증축 예비 | 프랙탈 — 새 workspace 생성 = 새 층 증축(자기복제의 시각화) |
| **좌석 = peer** | 상태 표기: 유휴 / 실행 중 / 투표 대기 / 정책 정지(blocked) | 이벤트 스트림이 유일한 상태 원천 — 연출 없음(원칙 7) |
| **빈 좌석 = 부재** | absence 카운터 표기(예: `견적 검토 공백 ×4/30d`) | 부재 기반 성장의 상시 가시화 — 임계 도달 시 채용 제안 카드(§8) |
| **2F 좌석 = 호스트 헬스** | Finn=T3610, Leo=GX10, Gus=Raspi — `infra` 이벤트로 카드 갱신 | 인프라 에이전트 역할의 직관적 표면화. 별도 상태 페이지 불필요 |
| **아바타 + Space** | 사람 아바타가 좌석 앞에서 Space → 해당 actor 사전 지정된 컴포저 열림 | 사람=최종 결정자의 신체화. 발신은 §3 정문으로만 |
| **회의실** | `vote_call` 발생 시 관련 peer들이 회의실로 이동, `vote_result`로 복귀 | 투표 프로토콜의 애니메이션 — 실제 이벤트 기반이므로 정직(원칙 7) |

뷰 구성: **오피스 뷰**(맵) + **타임라인 뷰**(스트림·리플레이) 2뷰. AI Office의 오피스/메신저 이원 구성을 우리 데이터 모델에 맞게 변용.

## 6. 명령 문법 【제안】

```
@Mike /fact-check $gitea 1042번 사안 인용 수치 원출처 대조해줘
```

파싱 → 정문 payload:

```json
{
  "channel": "office",
  "issuer": "human",
  "target_actor": "ra_us",
  "skills": ["fact-check"],
  "integrations": ["gitea"],
  "case_ref": 1042,
  "text": "1042번 사안 인용 수치 원출처 대조해줘"
}
```

- 살은 `@Mike`→`ra_us` 매핑과 문법 파싱만 수행. 라우팅·실행 판단은 전부 뼈대(원칙 3).
- n8n webhook `/gate/cmd` → OpenProject WP 생성 또는 기존 WP 코멘트 → 기존 mail-triage와 동일 파이프 합류.
- 멘션 없는 발신 = 직전 스레드(corr 체인) 계속 — AI Office 문법 차용.

## 7. 실행 거버넌스 【제안 — 뼈대 채택분, 살 아님】

AI Office 벤치마크에서 얻는 가장 실질적인 수확. 현 설계의 실제 공백이다.

| 정책 | 내용 | 집행 주체 |
|---|---|---|
| 동시성 상한 | 동시 실행 sub-agent ≤ **3** (T3610 32GB 실측 제약, DeerFlow 과제에서 확정된 수치) | n8n 큐 |
| 비용 예산 | 일일 토큰/비용 한도. 초과 시 `policy:pause` 발화 → 신규 실행 정지. **한도 값은 운영 실측 후 설정**(관찰 우선 — 지금 수치를 정하지 않음) | n8n + cost 필드 집계 |
| 재개 | 자동 재개 없음. 사람의 재개 명령(정문 경유)만 `policy:resume` — 원칙 4 정합 | 사람 → 정문 |
| 모델 폴백 체인 | 역할별: GX10 Qwen3(로컬) 우선 → 장애·부하 시 API 폴백. 폴백 발생은 `policy` 이벤트로 기록 | Hermes 설정 + n8n 헬스 체크 |

살의 역할: 예산 게이지·동시성 현황·폴백 이력의 **읽기 전용 패널** + 재개 버튼(정문 발신).

AI Office는 "자동 재개"를 제공하지만 우리는 채택하지 않는다 — 예산 초과 후 재개는 판단이며, 판단의 최종권은 사람이다.

---

## 8. 성장 시스템 — 증거 기반 채용 【제안】

AI Office의 "직원 채용" 버튼을 원칙 5의 절차로 재구성한다.

```
absence 이벤트 누적 → 임계 도달(gap_tag별 N회/기간) → hire_proposal 발화
  → 살: 빈 좌석에 채용 제안 카드 표시(근거 로그 첨부)
  → 사람 승인 → Gitea config PR → 사람 머지 → Hermes peer 생성
  → 다음 이벤트부터 새 actor 관찰 → 살이 좌석 자동 배치
```

- 판정 분기(원칙 5): 같은 철학의 공백 → **스킬 추가 제안** / 독립 직능의 공백 → **에이전트 채용 제안**. hire_proposal payload에 분기 판정 포함.
- AI Office와의 차이: 그들은 임의 채용(추측 기반 팀 추천 포함), 우리는 **부재 로그가 증거인 채용**. 조직이 데이터로 자란다.
- 임계값(N회/기간)은 【미결】 — 운영 데이터 확보 후 설정(관찰 우선).

---

## 9. 변경 관리 = config-as-code 【제안】

스킬 토글·모델 배정·정책 변경·채용 — 모든 구성 변경의 단일 경로:

```
살 UI에서 변경 제안 생성 → Gitea PR (diff 자동 작성) → 사람 리뷰·머지 → 뼈대 재적재
```

- UI 직접 쓰기 금지. AI Office의 토글 즉시 반영과 정반대 선택.
- 근거: (1) 원칙 4·6 보존, (2) 모든 변경에 이력·리뷰·롤백 — **의료기기 조직의 변경관리 문화와 동형**. 이 시스템 자체가 RA 도메인의 규율을 체화한다.
- SKILL.md 표준 스키마에 `trigger`(발동 조건), `inputs`, `outputs`, `owner_actor` 필드 추가 — AI Office의 트리거 키워드 문서화 관행 채택.

## 10. 외부 채널 【제안】

- **Telegram 봇 채택**: n8n 트리거(수신 명령 → 정문 payload) + n8n 응답(artifact 링크·결과 요약 회신). mail-triage와 완전 동형이라 추가 비용이 낮다.
- 보안: 허용 chat_id 화이트리스트(n8n 단에서 차단). 【미결】 명령 권한 범위(조회만 vs 지시 가능)는 운영 후 결정.
- Instagram 보류 — 도메인 무관.

## 11. 감사 리플레이 — 차별화 무기 【제안】

기록 재생 원칙(7)을 도메인 무기로 승격한다.

- **시간축 스크러버**: 하루/사안 단위로 오피스를 되감기 — 캐릭터 동선·회의실 투표·산출물 발생이 이벤트 그대로 재현.
- **사안 필터 재생**: "WP 1042가 어떻게 처리됐는가"를 3분 재생 — case_open→matching→handoff→vote→artifact→eval3 전 과정.
- **감사 내보내기**: 필터된 이벤트 체인을 JSONL + 정적 리포트로 내보내기.
- 의미: AI Office의 라이브 피드는 소비되고 사라지지만, 우리의 스트림은 **append-only 감사 증적**이다. 의료기기 RA 조직에서 이것은 장식이 아니라 실무 자산이다.

## 12. 단계 계획

선행 원칙: **계약 v2를 뼈대 2단계(mail-triage 이관) 착수 전에 고정**한다. 그래야 시스템 가동 첫날부터의 전 이력이 리플레이 가능하다. 이것이 이번 제안에서 가장 시급한 단일 결정이다.

| Phase | 내용 | 의존 | 산출물 |
|---|---|---|---|
| **0** | 계약 v2 확정 + Gitea 커밋, 기존 목업 v2 마이그레이션 | 없음 — **즉시** | event-contract-v2.md, 목업 JSONL |
| **1** | 창문: JSONL→SSE 게이트웨이(Raspi5P), 살이 실데이터 재생 | 뼈대 1단계(인프라 검증)와 병행 가능 — 단방향이라 안전 | relay 컨테이너, 살 DATA_SOURCE 교체 |
| **2** | 정문 확장: 오피스 컴포저 + Telegram → `/gate/cmd` | 뼈대 2단계(mail-triage) 가동 | n8n webhook 플로우 |
| **3** | 거버넌스: 동시성·예산·폴백 집행 + 정책 패널 | Phase 1·2 | n8n 정책 플로우, policy 이벤트 |
| **4** | 성장: absence→hire_proposal→Gitea PR 루프, 층 증축 | 뼈대 3단계(학습 측정) 이후 | hire 플로우, config 스키마 |
| **5** | 감사 리플레이: 스크러버·사안 필터·내보내기 | Phase 1 데이터 누적 | 리플레이 뷰 |

## 결론

AI Office에서 취할 것은 **문법과 거버넌스**(명령 문법, 실행 정책, 폴백, 트리거 문서화)이고, 취하지 않을 것은 **단일 평면 구조**(UI 직접 제어, 임의 채용, 토글 즉시 반영)이다. 우리의 9개 불변 축은 전부 생존하며, 유일한 긴장은 "명령은 정문으로, 관찰은 창문으로"가 해소한다. 결과물은 벤치마크의 편의성에 감사 증적·증거 기반 성장·학습하는 직원·로컬 추론을 더한 것 — 그들이 구조적으로 가질 수 없는 것들이다.

즉시 실행할 단일 결정: **이벤트 계약 v2를 mail-triage 착수 전에 고정.**
