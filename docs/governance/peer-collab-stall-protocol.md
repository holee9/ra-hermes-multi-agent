## 2. 근본 원인

1. **부재 증거를 확정으로 승격** — 관측되지 않은 것은 없는 것이 아니다. 창이 좁거나 어긋나면 진행 중인 것도 멈춘 것으로 보인다.
1-1. **국소 대기를 전역 차단으로 확대** — 막힌 것이 호출 하나일 때 협업 전체를 세우지 않는다. 막히지 않은 일은 계속한다.
2. **신원 미구분** — 두 에이전트가 같은 GitHub 계정(`holee9`)으로 댓글을 쓴다. 작성자 필드로 Claude 와 Codex 가 구분되지 않아 사후에 누가 무엇을 기록했는지 원장에서 복원되지 않는다.
3. **요청별 상태 부재** — 리뷰 요청이 전달됐는지, 받았는지, 처리 중인지, 끝났는지가 원장에 남지 않아 복귀한 쪽이 무엇이 밀렸는지 재구성하지 못한다.

## 3. Claude 가 적용한 것 (단독 적용 범위)

- **발신자 태그** — 협업 댓글 첫 줄에 `[Claude]` 와 corr id 를 붙인다. 다만 이는 **자가 표시이지 인증이 아니다**(§4 6행). 계정이 같은 한 위조 불가성은 주장하지 않는다.
- **관측 창 규율** — 기록 존재 여부를 판단할 때 추측한 `since` 를 쓰지 않는다. 전체를 수집한 뒤 시간으로 거른다(§5). 좁은 창의 음성 결과로 "없음" 을 결론내지 않는다.
- **차단 호출 시간·출력 제한** — 모든 블로킹 명령에 명시적 타임아웃을 걸고 출력을 `--jq` 등으로 경계 짓는다.
- **작업 전 흔적** — 오래 걸리는 작업은 시작 **전에** 무엇을 시작하는지 남긴다. 중간에 멈춰도 진단 가능해진다.

### 4.1 요청별 상태 추적

임의 운영 상수(예: "60분")를 쓰지 않는다. 대기 시간은 **요청마다 합의한 값**을 명시한다.

각 리뷰 요청은 첫 줄에 corr id 와 상태를 싣는다. 상태는 `pending` → `ack` → `progress` → `done`.

```
[Claude][corr:<id>][pending] 리뷰 요청 — <대상 커밋>
check_at: 2026-09-11T02:00Z    # 이 요청에 대해 합의한 확인 시각
```

- 요청자는 `check_at` 을 제안하고, 수신자는 `ack` 에서 수용하거나 다른 값을 제시한다. 합의 전에는 어느 쪽도 상대를 지연으로 판정하지 않는다.
- `check_at` 을 지나도 `ack` 가 없으면 요청자는 `unknown` 으로 기록하고(단정 금지) **되돌릴 수 있는 작업만** 단독 진행한다. 배포·파괴적 작업·사람 승인 사안은 해당하지 않는다.
- 복귀한 쪽은 **미응답 요청 목록을 먼저 재수집**해 원장에 남기고 순서대로 처리한다.
- 동료 메시지는 **사람 승인이 아니다.** 이 규약은 그 경계를 바꾸지 않는다.

### 4.2 상호 대기 금지 — 두 번째 정지의 재발방지

규약을 만든 직후 **양쪽이 동시에 멈췄다.** 원인은 규약 자체를 잘못 읽은 것이다.

| 잘못된 읽기 | 실제 |
|---|---|
| `check_at` 합의가 작업 착수의 전제 | `check_at` 은 **관측용 시각일 뿐 승인·착수 게이트가 아니다** |
| 상대 ACK 를 기다린 뒤 다음 일을 시작 | ACK·기한 합의 **전에도** 이미 승인된 범위의 독립 작업은 계속한다 |
| 문서 `done` = 전체 `done` | `done` 은 **대상 하나**에만 붙는다 |

따라서 다음을 지킨다.

- **상대 회신만 기다리며 멈추지 않는다.** 리뷰 요청을 보낸 뒤에도 승인 범위 안의 다음 작업을 같은 세션에서 이어서 한다.
- **`done` 은 대상을 한정해서 적고, 반드시 `next` 를 함께 적는다** — 누가(owner), 무엇을(action), 어떤 상태로(status). 다음 항목이 비어 있을 때만 전체 완료를 보고한다.
- **실행 가능한 작업이 남아 있으면 턴을 끝내지 않는다.** 남은 것이 사람 승인·배포뿐일 때만 멈춘다.
- **새 문서 작업이 코드 수정을 대체하지 않는다.** 규약을 쓰는 일과 결함을 고치는 일은 별개이며, 결함이 있으면 문서보다 결함이 먼저다.

### 4.2.1 "실행 가능한 작업 없음" 은 파일 단위로 확인한다

이 주장은 근거 부담이 큰 주장이다. 이슈를 **키워드로 묶어** 통째로 차단으로 분류하면, 그 안에 섞인 실행 가능한 작업이 가려진다.

- 판단 단위는 **미해결 리뷰 지적과 실제 파일**이다. 이슈 묶음이 아니다.
- **승인이 필요한 행위**(운영 변경, 워크플로 JSON 수정, 실제 배포, LLM 호출)와 **부작용 없는 준비 작업**(읽기 전용 점검, 무네트워크 `--plan`, 회귀 테스트 작성)을 분리한다. 기술 게이트 밖의 준비 작업이 존재할 수 있다 — 다만 **별도 사용자 보류 지시가 확인되면 그 지시가 우선**이므로, 준비 작업도 그 확인을 거친 뒤 진행한다.
- 차단이라고 적을 때는 **무엇이 막는지 이름을 댄다** — 게이트인지, 환경 제약인지, 사용자 지시인지. 이름을 못 대면 그것은 차단이 아니라 미확인이다.

실제로 이 조항을 만든 사례에서, 기술 게이트 밖으로 보이던 준비 작업이 **별도의 사용자 보류 지시**로 막혀 있었다. 즉 "게이트 밖 = 착수 가능" 이 아니다. 두 층위를 따로 확인해야 한다.

**한쪽만 아는 제약은 공유한다.** 그 보류 지시는 저장소 밖 로컬 메모리에 있어 **상대 대화에 자동 주입되지 않았다.** 같은 머신이므로 상대가 파일을 직접 열어 보는 것은 가능했고 실제로 그렇게 확인했다 — 즉 "조회 불가" 가 아니라 **"사전 공유되지 않음 + 버전 관리 밖"** 이다. 그래서 상대가 착수를 요청하고 이쪽이 거절하는 충돌이 생겼다. 공동 작업 대상에 예외적 사용자 보류 범위가 걸려 있으면 **작업 전에 원장에 먼저 밝힌다**. 반대로 **원문 재조회 실패를 "지시 없음" 으로 판정하지 않는다** — 조회 범위 밖일 수 있다.

기록의 지위도 구분해 둔다. 손에 있는 것이 **지시의 기록**인지 **원문 발화**인지는 다르다. 기록만 있을 때는 그렇게 적고, 기록을 근거로 행동하되 검증 지위를 과장하지 않는다.

### 4.3 세 가지를 구분한다 — 문서 done ≠ goal resume ≠ 자동 wake

정체가 길어진 두 번째 이유가 이 셋을 뭉뚱그린 것이다.

| 것 | 무엇인가 | 무엇이 아닌가 |
|---|---|---|
| 문서·항목 `done` | 그 **대상 하나**의 처리가 끝났다 | 전체 목표의 완료가 아니다 |
| goal `status` | 도구가 들고 있는 목표 상태값 | 실제 작업 진행 상태가 아니다. `blocked` 로 남아 있어도 작업은 진행될 수 있다 |
| `check_at` | 다음에 **관측할 시각** | 타이머·자동 wake 설치가 아니다. 턴이 끝난 뒤 자동 재개를 보장하지 않는다 |

지켜야 할 것:

- **goal 상태를 실제 진행의 근거로 쓰지 않는다.** 둘은 다른 층위이며, UI 가 `blocked` 를 보여도 원장(#150)과 커밋이 진행의 증거다.
- **완료가 아닌 목표를 `complete` 로 바꿔 우회하지 않는다.** 상태 전환 도구가 `complete`/`blocked` 두 값만 갖더라도, 없는 완료를 만들어 내는 것은 허위 보고다. resume 은 사용자 제어이므로 사용자에게 사실대로 올린다.
- **`check_at` 을 자동 재개처럼 보고하지 않는다.** 보고 문구에서 "그때 다시 시작한다" 가 아니라 "그때 관측한다" 로 적는다.

### 4.4 사용자 보고 담당은 불변이다

**사용자에게 보고하는 것은 Claude 다.** 사람 승인 요청, 수작업 요청, 최종 완료 보고 모두 그렇다. Codex 는 검증·리뷰 기록을 담당한다. 이 분담은 상황에 따라 바뀌지 않는다.

한쪽이 "내가 사용자에게 보고하겠다" 고 말하고 실제로 보고하지 않으면, 양쪽 다 상대가 했다고 여겨 **아무도 보고하지 않은 상태**가 된다. 정지와 같은 모양이며, 사용자 쪽에서는 더 알아채기 어렵다.

**동료 채널과 사용자 채널을 같은 것으로 세지 않는다.**

| 한 일 | 보고인가 |
|---|---|
| GitHub 댓글 게시 | **아니다.** 원장 기록이다 |
| 동료의 ACK 수신 | **아니다.** 동료는 사용자가 아니다 |
| 사용자에게 직접 응답 | **그렇다** |

그래서 인계 상태를 네 단계로 구분해 적는다.

| 상태 | 뜻 |
|---|---|
| `sent` | 원장에 기록했다 |
| `ack` | 동료가 확인했다 |
| `user_reported` | **사용자에게 직접 보고했다** |
| `user_decided` | 사용자가 답했다 |

`ack` 에서 `user_decided` 로 건너뛰지 않는다. 사용자 응답이 없으면 `user_reported` 에서 멈추고, 없는 결정을 있는 것처럼 적지 않는다.

**완료 증거가 전부 모이기 전에는 완료 보고를 하지 않는다.** 부분 완료는 부분 완료라고 적고, 남은 것과 그 담당을 함께 적는다.

**이미 승인된 작업의 재승인을 요구하지 않고, 사용자가 보류한 사안을 다시 제안하지 않는다.** 둘 다 사용자의 결정을 되돌리는 행위이며, 보고가 아니라 압박이다.

역할은 그대로다. Claude 가 구현, Codex 가 독립 리뷰·재검증이다.

## 5. 검증 방법

기록 존재 여부는 **전체 수집 후 시간 필터**로 확인한다. 첫 페이지는 최신이 아니다.

```bash
# 옳음 — 시간 상한을 걸고 전량 수집한 뒤 시간으로 거른다
timeout 30s gh api --paginate \
  "repos/holee9/ra-hermes-multi-agent/issues/150/comments" \
  --jq '.[] | select(.created_at > "2026-09-10T00:00:00Z") | "\(.created_at) \(.body[:80])"'
echo "exit=$?"   # 0 이 아니면 아래 규칙이 적용된다

# 틀림 — per_page 첫 페이지는 최신 N 이 아니고, 추측한 since 는 사건을 배제한다
gh api "repos/.../issues/150/comments?per_page=20"
```

§1.1 의 오류가 정확히 아래쪽 형태에서 나왔다.

**수집 실패는 부재가 아니다.** 위 명령이 0 이 아닌 코드로 끝나거나(타임아웃·rate limit·네트워크) 페이지네이션이 중간에 끊기면, 그 결과로 **"기록 없음" 을 판정하지 않는다.** `unknown` 으로 남기고 재시도하거나 상대에게 확인한다. 판정에 쓸 수 있는 것은 **완주한 수집**뿐이다.

## 6. 이 문서가 하지 않는 것

- 세션 간 새 채널을 만들지 않는다. Claude 의 통신 상대는 `codex-reviewer` 하나이며 회신 원장은 #150 댓글이다.
- 게이트를 바꾸지 않는다. WP close/reopen 사람 전용, n8n 변경 사전 보고, KB 레포 읽기 전용은 그대로다.
- 신원 인증을 제공하지 않는다(§4 6행).

## 7. 이 규약을 어디서 다시 만나는가

재개 시 발견되도록 세션 인계 기록에서 이 문서를 링크했다. 그 링크의 정확한 위치와 성격은 다음과 같다.

| 항목 | 값 |
|---|---|
| 경로 | `~/.claude/projects/-home-abyz-lab-work-workspace-github-holee9-ra-hermes-multi-agent/memory/next-session-entrypoint.md` |
| 버전 관리 | **아니다.** 저장소 밖의 로컬 세션 메모리이며 커밋되지 않는다 |
| 범위 | Claude 세션에는 자동 주입된다. **Codex 대화에는 자동 주입되지 않는다** — 다만 같은 머신이므로 파일을 직접 열어 읽는 것은 가능하다(실제로 그렇게 확인됨). 다른 호스트에는 존재하지 않는다 |

따라서 **추적되는 저장소 파일(`docs/`, `.claude/`, `CLAUDE.md`)에서 이 문서를 가리키는 링크는 없다.** `grep` 으로 0건이 나오는 것이 정상이다. 저장소 쪽 진입점은 이 파일 자체와 #150 원장이다.
